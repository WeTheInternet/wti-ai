# Ideas and Loose but Valuable Directions

## Purpose

This file preserves important thoughts that are not yet ready to harden into law.

## Rich but optional deliberator roles

Starting roles worth remembering:
- advocate
- opponent
- critic
- mediator
- dreamer
- expert
- product user
- developer
- project manager

The implementation can start smaller, but these perspectives matter.

## Agent influence models for later

Future possibilities worth preserving:
- role-weighted agent judgments
- human-delegated trust
- auto-approve thresholds for low-risk sessions
- domain-specific consensus models
- agent follow-trust / vote-for structures

None of these should be frozen yet.

## Conditions as a powerful primitive

A judgment or refusal with conditions may be more powerful than a flat yes/no.

Example:
- "I oppose this unless missing fact X is supplied."

Once X is supplied, the system can revisit and potentially resolve the objection cleanly.

This feels important enough that conditions should likely be present from early design.

## Opposition should stay alive

A strong rejected point should not disappear just because the system moved on.

The architecture should preserve:
- dissent
- minority concerns
- rejected-but-salient arguments
- archived counterproposals

This is valuable for later reconsideration.

## The build-graph intuition

The user's instinct that changing truth should dirty dependent things is good.

The project should remember this intuition while staying cautious about premature complexity.

## Graveyard matters

The user repeatedly emphasized that:
- replaced truth should not poison active truth
- old reasoning should remain findable
- full archaeology matters
- `.knowledge/graveyard` might even be optionally ignored in some downstream contexts

That idea should remain visible in the design.

## Legal and governance future

The architecture should leave room to grow into:
- law-like rule editing
- stricter consensus models
- voting/weighting
- multiple human participants
- legal or policy traceability

But software delivery remains first priority.

## Human-natural interfaces

The conversation strongly suggests that the project wants:
- graph underneath
- thread-like interaction on top
- summaries at branch resolution
- multiple dedicated panes by activity type

That combination feels more promising than either pure chat or pure graph UI alone.

## Working reminder

Do not lose velocity in pursuit of theoretical completeness.
